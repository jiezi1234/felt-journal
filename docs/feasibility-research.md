## 1. 执行摘要

### 1.1 结论及成立条件

**核心闭环具备技术可行性，但当前项目尚不能据此认定为可稳定上线。** 普通记录、板面编辑、月历、导出等已有实现和自动化证据；真正决定交付的是主体提取质量与正式网络接入、本地容量与故障一致性、隐私授权及平台审核。记录仅在本机保存不等于照片不经过服务器，也不等于本机记录可以无限增长。

| 结论编号 | 最重要结论 | 性质、证据与置信程度 | 交付含义 |
| --- | --- | --- | --- |
| C01 | 照片选择、Canvas 布置、文字分类、月历、1800×1200 PNG 导出有实际技术路径 | 已确认；L01–L06、W01–W09；高 | 沿用现有原生架构，没有必要为首版重写跨端工程 |

| C03 | 手机正式主体提取链路尚未获得完成证据 | 已确认；正式配置为 `unconfigured`，私有工具配置关闭域名校验；L02、L04、L07、W03；高 | 先验证 HTTPS、合法域名、证书、备案和手机上传下载；localhost 成功不能作为发布依据 |

| C07 | 仓库已包含 P1，现行删除语义已变更为多板引用 | 已确认；需求顶部补充、L01、L03、L08；高 | 不按旧正文回退为“一条记忆只属于一个板”；保留现有数据关系，分别验收 P0 和 P1 |

**推荐架构：原生小程序 WXML/WXSS/JavaScript＋统一 Canvas 2D 渲染＋本机文件/版本化元数据＋可替换的 HTTPS 提取服务。** 优先复用 FastAPI、Pillow、rembg/ONNX Runtime 的现有服务做质量和资源 PoC；以腾讯云数据万象通用抠图作为合理备选，满足质量、价格、地域与隐私条件后再决定是否替换。首版不引入云端生活记录数据库。架构推荐为经验判断，置信度中高；正式选定推理引擎以 P01/P04 验证结果为条件。

### 1.3 证据与置信程度约定

- **已确认事实**：官方原文、直接读取的代码或本轮可复现输出支持；不扩大事实的适用范围。
- **经验推断 / 推荐**：工程判断、资源和工时估算，标注假设；不是平台承诺或供应商报价。
- **待验证**：缺少实际账户信息、目标设备、服务开通状态或 PoC；必须通过第 5 节实验解除。
- **高 / 中 / 低置信度**分别表示：直接证据充分；路径明确但依赖未实测条件；证据缺口较大。高置信度也不表示平台未来不会变化。

### 2.3 核心依赖和数据模型

```text
主体支持范围 / 存储容量口径 / 主体与类目 / 隐私用途
    ├─ 质量与容量 PoC ── 推理服务选择 / 本地数据组织
    └─ HTTPS、域名、服务身份、额度 ── 手机真实上传下载

照片选择 → 原图持久化 → 提取 / 明确原图降级 → 主体图持久化
                                              ↓
                                  Memory＋默认 Placement 提交
                                              ↓
                              统一板模型与渲染器 → 浏览/编辑/详情
                                              ├─ 首页与月历预览
                                              └─ 导出 → 相册 / P1 图片分享

主题复用 → 多板独立 Placement → 引用删除规则 → 安全文件回收
```

- **Memory**：记忆 ID、原始记录日期、原图/主体文件、主体宽高、文字、分类、创建/更新时间、处理状态或版本。当前 `boardId` 保留为来源日期，不再表示唯一摆放板。
- **Board**：每日板以本地 `YYYY-MM-DD` 标识；主题板用独立 ID；保存颜色、纹理及摆放集合。
- **Placement**：板、记忆引用、中心位置、宽高、角度、层级、加入板时间；跨板布局独立。
- **本地技术记录**：任务幂等映射、布局/文字草稿、待回收文件、schema/revision。它们同样占空间，不能只估计可见内容。
- **服务临时结果**：随机令牌、过期时间、访问控制；不属于用户云备份。取消、失败、到期后应回收。

上述关系已在 v2 代码中体现（L03，高）。若未来转独立数据库，以 `(board_id, memory_id)` 唯一约束防重复摆放；数据库事务只覆盖数据库，照片对象存储仍需“两阶段引用提交＋补偿清理”（工程建议，中；S10）。

### 2.4 管理端边界

产品没有提出独立业务管理网页，首版无需增加。必要的管理工作是：微信主体/备案/类目/隐私配置，服务密钥与发布配置，处理成功率、耗时、拒绝量、CPU/内存、临时文件清理、预算告警和故障排查。可先用微信后台、云服务控制台和受限运维入口完成。不得在监控中默认采集用户原图、记忆文字或带有效下载令牌的完整 URL。（范围判断，L01；经验建议，中高）

| 历史空板恢复 | P0 历史空板不补记；P1 移除后 Memory 仍在 | 已移除的旧 Memory 可放回原日期，不等于向从未记录的历史日期补记 |
| 导出与分享 | 文字/日期是否绘入作品未最终确定 | 当前作品是板体与物件，无日期、主题名、记忆文字；P1 是图片分享，不是接收方云记录链接 |

以上为 L01、L03–L05、L08 的直接比较，高置信度；具体产品决策均为**待确认**。

### 3.2 图片处理的技术路径与边界

**现有链路事实（L04、L07，高）：**

1. 系统选择器返回单图，客户端先复制原图到自己的持久目录。
2. `wx.uploadFile` 以 multipart 的 `photo` 字段上传；客户端超时配置 60 秒，上传达到 100% 后显示提取阶段。
3. 后端只解码 JPEG/MPO 首帧、PNG、WEBP；最大 15MiB、2400 万像素；按 EXIF 纠正方向，再转 RGB、最长边缩至 2048。
4. rembg 的 `isnet-general-use` 在 ONNX CPU 上执行，清理弱孤立 alpha，拒绝近乎全透明/全不透明结果，主体裁边并合成细边缘。
5. 随机 PNG 结果 URL 标称有效期 900 秒；客户端下载、持久化、读图成功后提交记忆和默认摆放。阴影由客户端统一渲染器绘制。

这些检查只能判断“有非平凡 alpha”，**无法判断提取的是不是用户想要的主体，也无法证明毛发、玻璃、花束等效果合格**。后端对输入透明 PNG 转 RGB 也可能改变其原有 alpha 语义；是否允许上传已有贴纸需产品确认后专项测试。

**历史证据（A01、A02，中）：**三个公开 ISNET 样例留存推理耗时约 1.81–4.94 秒；一次开发者工具真实链路记录 2023ms。它们来自少量、不同运行状态样例，没有统一机器/冷暖启动统计，不是 P95、不是手机公网 SLA，也不能用 4.28 秒的 u2netp 旧样例推断当前模型性能。

**推荐处理边界（经验建议，中）：**原图本地保留；仅为推理另建尺寸/格式归一化副本。照片字节、像素、方向、颜色、透明度都应校验；不能只校验文件扩展名。压缩上传副本可以降低弱网耗时，但不能擅自替换产品要求保留的原图。2400 万像素限制在缩图之前执行，48MP 原图可能被直接拒绝；“手机能选”不等于后端能解码。P03 应决定客户端兼容转换是否足够，还是需要补充服务端解码。

同步请求可以保留为小流量首版路径。若公网 P95 不能满足用户等待目标，应采用“短上传请求→任务 ID→有限轮询/结果取回”，服务器管理超时和 TTL；图片处理仍不做跨会话草稿自动恢复，除非产品另行授权。不能仅增加 Caddy 超时来解决微信切后台后的中断。（W03、W13；工程推断，中高）

### 3.3 本地存储：必须先解决的架构边界

**官方确认，截至 2026-10-14（W01、W02，高）：**本地缓存文件与本地用户文件合计最多 200MB；Storage 单 key 最大 1MB、整体 10MB。这是两类不同限额。临时文件不是长期记录容器，不能因为其空间更大就用临时路径代替持久文件。Storage 也可能因用户操作或系统存储原因被清理，不提供应用级备份保障。

当前主快照存在 `felt-journal:v1` 单 key 内，内部 version 为 2，全部板、记忆、操作幂等映射和垃圾队列每次一起序列化。`get()`、校验、查询和提交会克隆或遍历全量状态；数据变多会同时影响容量和响应时间。`operations` 在新增/替换/裁剪时增长，删除记忆不会同步缩减这一历史映射。（L03，高）

**照片容量规划示例：**假设原图平均 3MiB、主体图平均 1MiB，只为长期图片预留 160MiB，约只能容纳 `160÷(3+1)=40` 条；若每天 3 条，约 13 天。若原图平均 1MiB、主体 0.3MiB，则约 123 条。这里的照片大小和 160MiB 预留均是假设，**不是实际测得平均值或产品总量限制**。缩略图、替换时新旧并存、未提交任务和垃圾回收积压还会占空间。当前“使用原图”降级也会另存主体副本，可能接近双份原图体积，不能套用透明主体较小的假设。（L03、L04，高）

**本轮合成元数据测量（不写微信存储）：**使用当前 `geometry.create`、store 校验和 v2 schema，每天 3 件，固定示例文件路径，每条一个幂等操作，文字为空或 1000 个汉字。没有主题板、额外替换历史、草稿和积压垃圾。

| 记忆数 | 每条文字 | JSON UTF-8 字节 | JavaScript UTF-16 单位数 |
| --- | --- | ---: | ---: |
| 100 | 空 | 60,117 | 59,517 |
| 100 | 1000 汉字 | 360,117 | 159,517 |
| 300 | 空 | 180,515 | 178,715 |
| 300 | 1000 汉字 | 1,080,515 | 478,715 |
| 600 | 空 | 361,215 | 357,615 |
| 600 | 1000 汉字 | 2,161,215 | 957,615 |
| 1095 | 空 | 659,371 | 652,801 |
| 1095 | 1000 汉字 | 3,944,371 | 1,747,801 |

测量结论置信度高；**不能据此断言“第 300 条一定写入失败”**：微信 Storage 对该对象/字符串大小的实际计量、路径长度和设备行为仍待 P02 验证。足以确认的是：长期全量单 key 不是有余量的扩展方案，拆分元数据也不能突破 200MB 图片限额。

推荐先选定产品容量口径，再实施存储治理：

- 统计引用文件总量和预期新增字节；添加/替换前预留新旧并存空间；满额时保留旧记录并拒绝新增，不能自动删用户原图。
- 根据目标体量采用按月/板分片或用户文件中的版本化快照；小 Storage 仅放索引和当前版本。跨板引用、彻底删除和 schema 升级仍需一致性设计。
- 若采用文件快照，使用新版本文件写入、校验、切换小型版本指针、保留上次可读版本，再清理未引用文件；rename/写入及指针切换的崩溃行为须在目标环境验证，不能直接称为可靠事务。
- 缩略图和渲染副本可重新生成，不等同于原图；导出作品只有合成像素，不能还原可编辑的 Memory/Placement。
- 如果产品要求大量多年照片且保留原图，现有“纯本地、无云备份”约束下容量无法无条件满足。应由产品选择容量边界或后续备份方案，不自行把云同步提前到 P0。

以上为必要的可靠性实现建议（中高），不是本轮代码变更。

| 社区/协作/商城 | 通用后端、权限、审核、订单/支付可构成方案 | 公开范围、并发编辑策略、商品性质、交易资质和支付规则 | 不给笼统“可上线”承诺；需独立需求与官方规则调研 |

## 4. 技术选型对比

比较中的成本、性能、维护和扩展性是基于当前项目的工程判断（中置信度）；官方资料只证明能力/限制，不证明某框架对本项目一定更快。

### 4.1 原生与跨端框架

| 方案 | 难度与开发成本 | 运行性能 | 可维护性 / 扩展性 | 平台限制与适用场景 |
| --- | --- | --- | --- | --- |
| **原生 WXML/WXSS/JS** | 当前工程最低增量成本；Canvas/文件直接接入 | 少一层框架状态适配；仍受 Canvas、setData、解码限制 | 团队需熟悉微信；现有模块和测试可复用 | 本项目只明确微信端，优先推荐 |
| Taro 4.x（React/Vue） | 新项目中等；当前迁移要重做页面和回归 | 能调用 Canvas；不能消除宿主资源上限 | 多端 UI/逻辑可复用，需维护平台专用适配层 | 多端目标明确且团队熟悉时合理；Canvas 支持不代表全部端相同。S08 |

跨端是合理替代，但本轮没有需要迁移的证据；不为了首版额外叠加第三套框架。无需 TypeScript 重写才能交付，后续可在稳定模块增量采用类型检查。（L02、S08；推荐中高）

### 4.2 本机记录、独立后端与云开发的边界

| 方案 | 难度 / 开发与运行成本 | 性能与维护 | 扩展性 | 平台限制 / 本项目适配 |
| --- | --- | --- | --- | --- |
| **本机记录＋独立提取服务** | 复用最多；无云记录数据库费用；承担推理机器/带宽/维护 | 本地浏览离线可用，推理需联网；自己负责升级、限流和可用性 | 可换推理实现；记录仍受本机容量约束 | 与 P0 无账号、无云备份最吻合 |
| 本机记录＋CloudBase/微信云托管容器 | 部署运维门槛较低，但需验证镜像、模型下载和常驻费用 | 托管扩缩容；冷启动、可写临时目录和实例内存必须测 | 适合多实例、后续云功能；不必启用云数据库 | 云托管私有访问与现有 uploadFile 协议需实证；不能仅有样例函数就视为接通。S09 |
| CloudBase 数据库＋云存储＋函数/容器 | 需要身份、隔离规则、迁移和远端删改；不是零成本 | 云数据库/存储维护较少，网络与资源配额影响体验 | 后续账号备份快；与供应商能力耦合 | 仅作为 P2 云备份备选，不擅自替代本地 P0；S07 |
| 独立 API＋PostgreSQL＋对象存储 | 初始工程与运维成本较高 | 自管关系事务/监控，图片对象独立 | 复杂引用、权限、协作和跨系统扩展较清晰 | P2 复杂业务才有必要；S10 |

普通云函数并非绝对不能运行推理，但当前模型、运行时依赖、冷启动、内存和包分发尚未验证。优先评估容器或常驻服务；不能把“函数超时配额很长”当作用户端能稳定等待的证据。（经验建议，中；S07、S09、W03）

### 4.3 元数据与文件存储

| 方案 | 难度 / 成本 | 性能 | 一致性、维护与扩展 | 限制与适用范围 |
| --- | --- | --- | --- | --- |
| 当前全量单 key JSON＋本地图片 | 已有实现，短期最低 | 小数据简单；每次全量克隆/校验/写入 | 跨模型同次写入易理解，扩大后耦合严重 | 1MB 单 key；仅适合验证或明确小容量范围，不推荐无边界长期记录 |
| 按月/板拆分 Storage＋小索引 | 中等，需要写入日志/恢复与迁移 | 局部读写降低全量成本 | 多 key 没有自动跨 key 事务，主题跨月引用增加复杂度 | 总 10MB，单 key 仍 1MB；需 P02 验证 |
| **用户文件版本化快照/分片＋小型 Storage 索引** | 中高，需双版本恢复和清理 | 可按月懒加载；仍需测同步 I/O | 便于保留旧版本，必须解决切换和跨板引用恢复 | 与图片共享 200MB；是本地架构候选，不能解决照片总容量 |
| 云文档数据库＋云对象存储（P2） | 中；增加用户身份与安全规则 | 云读写/网络/索引计费 | 小团队运维省，复杂关系仍需事务/补偿验证 | 私有规则不能设全员可读；不合 P0 无云备份边界 |
| PostgreSQL＋COS 等对象存储（P2） | 高；需要后端和运维 | 关系查询/索引可控 | 明确唯一约束和事务；对象生命周期独立 | 适合复杂协作，不建议首版引入 |

微信小程序环境没有本报告已确认、可直接按 Node.js `sqlite` 使用的通用数据库运行时。为此引入大型 WASM 数据库没有当前需求依据，不作为首版必要选项。（调研边界，中）

### 4.4 自动提取：自托管与商业 API

| 方案 | 难度 / 开发成本 | 运行成本与性能 | 维护 / 扩展性 | 输入、平台与适用条件 |
| --- | --- | --- | --- | --- |
| **现有 rembg＋ISNET CPU** | 当前最低；已有链路和本地样例 | 固定机器、网络成本；真实吞吐待压测 | 自己维护模型、依赖、质量和升级；模型可替换 | 自有处理更可控；目前 15MiB、2400 万像素、2048 边长为本项目值；复杂透明物体不保证 |
| **腾讯 CI `AIPicMatting`** | 中，后端 SDK/签名、COS/CI 服务开通、结果转接 | 查到通用抠图 0.02 元/次，COS/流量等另计；服务耗时待测 | 模型维护少；服务可用性/配额/费用依赖供应商 | 官方限制 PNG/JPEG/JPG、≤10MB、32×32 至 7680×4320、文档默认 5QPS；需确认目标账户与地域。S04–S06 |
| 阿里云 `SegmentCommonImage`（条件备选） | 中，SDK/权限、格式缩放、临时结果接收 | 官方页列起始按量 0.002 元/次；不是最终总成本 | API 路径明确，但文档标记停止维护且有套餐变更，需确认仍可新开通与支持承诺 | ≤3MB、最长边≤1999、四通道 PNG，临时结果 30 分钟；不直接满足任意原图上传。S11–S12 |

**调研判断：**商业 API 具有合理替代价值，但质量不预设优于当前 ISNET。腾讯应先做同样本 A/B；阿里云当前只作为条件备选，不能凭较低单价直接选定。商用调用必须经后端或受限临时凭据，不能把永久密钥放客户端。（中置信度；P01/P04 待验证）

rembg v2.0.85 代码许可为 MIT；ISNET/DIS 上游代码与评估使用 Apache-2.0，数据集有单独条款。**代码许可不能自动证明所有下载权重、转换产物和训练数据的商业授权范围相同。** 上线前记录具体权重来源、版本/哈希、许可和必要通知；不能未经核对把模型切到其他权重。没有断言当前权重禁止商用，也没有将许可链核验认定为完成。（S01–S03，高；具体授权材料待验证）

### 4.5 客户端与服务端职责、同步与异步

| 选择 | 难度、性能、可维护性与成本 | 平台限制 / 适用结论 |
| --- | --- | --- |
| **客户端 Canvas 负责布局/导出** | 已有；交互即时、无每次导出服务费；同源渲染减少屏幕/作品不一致 | 小程序像素内存/设备差异要测；推荐首版 |
| 服务端 Pillow/图形服务合成导出 | 需上传布局/素材并保持同一纹理算法；增加流量、隐私面和维护 | 若客户端出口性能实测无法达标，作为替代；不是首版默认 |
| 客户端神经网络主体推理 | 模型下载、WASM/WebGL、算子和机型资源适配成本高 | 理论不排除，当前没有通用照片质量/内存证据，不作稳定 P0 依赖；待独立 PoC |
| **服务端主体推理** | 当前 Python 模型及商业 API 都能适配；可统一模型和资源控制 | 需要联网、预算、身份与临时数据治理；推荐 |
| **同步上传→结果 URL** | 简单、复用现有代码；无需队列/任务库 | 暖服务在目标延迟内可保留；后台中断和峰值拒绝必须处理 |
| 异步任务＋有限轮询 | 增加任务状态、幂等、TTL 和轮询请求；资源调度较清晰 | 当冷启动/耗时/峰值不能满足同步目标时启用；不自动增加跨会话草稿恢复 |

结论依据 L04–L07、W03/W06/W13/W14；方案比较为中置信度工程判断。无合理理由为简单文字、分类、月历购买第三方服务，这些应保持本地实现。

## 5. 高风险问题与 PoC 验证计划

### 5.1 执行原则和当前状态

按“会改变架构或阻止上线”的顺序执行 P01→P02→P03/P04，再做设备体验和完整发布验收。实验使用合成数据或经授权样本、隔离 AppID/测试存储，不能覆盖用户真实记录。每次保存设备/微信/基础库/服务器规格、网络、输入大小与结果版本；记录原始数据，不只记录“通过”。本轮没有执行下列正式 PoC，状态均为**待验证**，已有历史结果仅作线索。

验收指标为建议目标，不是原需求新增约束；产品确认后再成为合同或验收门槛。风险等级依据“发生可能性×损害范围”，高表示可阻断核心流程、破坏数据或导致资源失控。

### P01：主体质量、正式网络和服务选择（高，最高优先）

- **依据**：主体提取是 P0 核心；正式 endpoint 未配置；现有只有少量公开样例。相关资料 W03/W05、S01–S06、L04/L07、A01/A02。
- **最小实验**：准备 60 张有权使用的照片，覆盖食物、杯子、花束/植物、动物毛发、人物、玻璃/半透明、低对比、多主体；记录期望主体。现有 ISNET 与腾讯通用抠图同样本 A/B；至少两名评价者按“无需修整可放板 / 可识别但明显缺陷 / 不可用”盲评，争议由产品判定。部署独立测试服务，iOS/Android 各一台，在 Wi-Fi 和移动网络下关闭微信调试、开启合法域名校验，至少各完成 20 次上传→下载→保存→回板。
- **建议验收**：主体定义可被产品说明；普通目标场景“直接可用”≥90%，挑战样本单列不掩盖失败；各平台链路完成率≥95%，建议端到端 P50≤5s、P95≤12s（质量样本和性能重复次数不足以证明生产 SLA，只用于初选）；无错板、重复记录；全部失败可明确重试/原图/取消。
- **失败替代**：优先切换提取引擎、预热/优化上传副本、调整计算规格；长耗时改异步。若核心目标场景仍不满足，重新确认产品支持范围；不能默认把自动提取从 P0 删除。
- **需留存**：原始分类评分、同尺寸结果、调用次数与账单、设备/网络耗时、HTTPS 关闭调试证据。实际付费开通/上传真实照片应在后续执行时按授权范围进行，本轮仅计划。

### P02：存储容量、单 key 上限和崩溃恢复（高）

- **依据**：已确认 200MB 文件与 1MB 单 key 上限；全量快照和保留原图直接触碰边界，可能使整应用无法新增/保存。资料 W01/W02、L03/L04、3.3 测量。
- **最小实验**：在隔离测试小程序中逐步写 100/300/600/1095 条元数据，分别测试空文、1000 汉字、emoji、主题引用和大量换图任务；测每次写入与冷启动耗时、实际字节、错误。持久图文件逐步增至 120/160/190MB 并越过实际限额，测试新增/替换双份空间。分别在“文件复制后、关系提交前、索引切换后、垃圾回收前”强制关闭进程并冷启动。
- **建议验收**：实际单 key/总文件限额记录清楚；容量将满时拒绝新增而不伤旧数据；所有注入中断都恢复为旧完整版本或新完整版本，无 Memory 指向缺失图、无跨板错删。目标容量下建议单次保存 P95≤200ms、冷启动本地数据加载≤1s；容量目标先由产品明确。对声称支持的边界做至少 30 轮故障注入。
- **失败替代**：版本化文件/分片和完整迁移；保留恢复点、限制并行写入。若原图总量不能满足预期，仅能由产品确认总量/保留策略或 P2 备份路线；不自动删图、压缩原图或提前云同步。

### P03：真实手机照片格式、方向和大图（高）

- **依据**：后端拒绝 HEIC 等格式和超过 2400 万像素图片；15MB 合格不代表像素合格，影响拍照核心入口。资料 W04、L04/L07、S05、S11。
- **最小实验**：iPhone HEIC/Live Photo 交付、Android 普通/48MP 照片、MPO、带 8 种 EXIF 方向的 JPEG、透明 PNG、WEBP、全景、超大像素、小文件压缩炸弹和损坏文件，至少各 2 份；走真实 chooseMedia→读取→上传。核对原图副本、主体方向和导出颜色/透明度。
- **建议验收**：声明支持的格式全部成功，非支持格式稳定给出明确反馈；无无声旋转、镜像或原图损坏；大图拒绝不会拖垮服务。归一化副本转换后仍保留原图引用；不把 48MP 简单统称网络错误。
- **失败替代**：客户端 Canvas/JPEG 生成上传副本（先验证 iOS/Android 解码）、服务端受控格式转换或商业引擎适配；如不能支持，明确支持范围并由产品确认。

### P04：推理资源、匿名访问与并发（高）

- **依据**：当前进程一次推理、忙返回 503；锁在上传和解码后，公开请求可消耗内存；无认证和配额。Compose 限 CPU 2、内存 3GB 是配置，不是性能证明。资料 L07、W03/W15、S09。
- **最小实验**：在候选部署规格上预热后，以并发 1/2/5/10 和 1MB/5MB/15MB 输入测试；记录 CPU、RSS 峰值、上传/解码/推理各阶段、P95/P99、拒绝率。测试冷启动、模型下载断网、磁盘满、过期令牌、重复 taskId、伪造 Referer、取消后资源释放。验证 `wx.login` 短期令牌或云托管身份与“不弹账号页”兼容。
- **建议验收**：选定目标峰值下成功请求满足 P01 延迟目标；超量在入场阶段可控拒绝，无 OOM/无限队列；身份失效不能调用昂贵推理；日志不含原图/有效下载凭据。正常满负荷 RSS 建议留≥30%余量；24 小时稳定性观察和账单上限告警有效。
- **失败替代**：更大内存/独立上传限流、解码信号量、有限任务队列、增加实例或商用 API；多实例结果须共享临时对象存储或确保路由一致。增加 worker 会重复加载模型，不能当作免费扩容。

### P05：隐私、主体资质与提审（高）

- **依据**：后台状态不可由代码读取确认；实际传照片；本地提示不能代替隐私同意。资料 W07–W12、L02/L04/L07。
- **最小实验**：产品/主体管理员核对类目、备案、隐私用途、接收服务与保留期；使用全新测试用户体验版验证首次同意、拒绝、再次同意、更新用途后的再次确认、相机/相册拒绝与设置恢复；核查处理服务器与代理日志、TTL 及重启清理。
- **建议验收**：同意前不上传照片；拒绝后已有记录可浏览；相册拒绝不会误报保存；声明与实际数据流一致；服务不把原图落盘、不在日志泄露用户内容；过期结果不可取且物理清理时限有验证。审核材料与功能一致，取得平台实际审核结果后才标记审核通过。
- **失败替代**：补齐官方授权链、修正配置/接收方、选择符合要求地域的服务；保持本地回看和原图路径可用。类目/资质不满足时先解决主体与实际业务匹配，不能靠隐藏功能绕过审核。

### P06：30 件板面、月历和导出内存（高）

- **依据**：单张 2048² RGBA 解码约 16MiB；30 张理论像素数据约 480MiB，远大于 PNG 压缩体积；还有显示/导出 Canvas、纹理和缓存。这个计算不是微信官方内存上限，也不是当前实际峰值。资料 L05、W06/W14。
- **最小实验**：低内存 Android、常用 Android、iPhone 各一台；1/10/30 件 512/1024/2048 主体；连续拖动/旋转/撤销、首页多预览、日历快速切月、反复开详情和生成 1800×1200 图片各 20 轮。记录帧间隔、长任务、可用内存、失败与退出。
- **建议验收**：30 件目标尺寸下无崩溃/白屏/持续内存增长；建议拖动 P95 帧间隔≤33ms、导出≤3s；输出全部物件、层级、背景和边框正确、无工具；不同设备允许抗锯齿细微差异，不要求跨设备像素完全相同。
- **失败替代**：渲染专用小图/缩略图、限制缓存并在页面销毁释放、按帧合并绘制、纹理缓存、分批加载；原图保持。若仍失败，评估服务端导出；降低作品尺寸或 30 件上限需产品决定。

### P07：中断、一致性、多板删除和版本迁移（高）

- **依据**：多 Board 引用、图片换新、未保存草稿与晚到回调交错，可能造成错板或数据丢失。资料 L03/L04/L08、W13、A03/A04。
- **最小实验**：固定时钟跨零点；上传/下载/保存中取消或离页；重复成功回调；文件保存失败后重试；一记忆两主题板；移除→放回→旧草稿保存；删板/全局删除和换图并发；v1 原始记录升级时注入写失败。每个窗口至少 10 轮，核对图哈希与引用图。
- **建议验收**：无错日期、重复记忆、旧草稿复活已删内容；换图失败旧图/布局完好；只移除摆放/删主题不删共享照片；全局删除覆盖全部引用；读取 v1 不写回，失败仍可读旧记录；取消任务不出现迟到插入。
- **失败替代**：串行提交、任务/成员/照片版本校验、恢复日志和幂等记录生命周期设计；不能用“多重重试”掩盖半提交。

### P08：图片分享参数与真实接收（中高；若首发 P1 则为发布门槛）

- **依据**：分享替身只验证调用；`needShowEntrance` 比函数本身版本要求更高；当前公私基础库不一致。资料 W09、L02/L05、A04。
- **最小实验**：iOS/Android 当前稳定微信与产品选定最低版本；实际用户点击后手动发送测试图片，接收方核对清晰度、完整边框、是否带小程序入口；测试取消、相册拒绝、临时文件失效、第二次生成后分享。由测试者手动选接收方，本轮不发送。
- **建议验收**：接收图构图与预览一致；旧端无能力则显示相册路径；无需入口的产品语义在目标版本可达；不声称消息已送达、相册已保存。
- **失败替代**：保留 P0 相册导出后用户自行分享；明确最低版本或延后 P1 分享，不把带本地 Memory ID 的页面卡片当成接收方可读记录。

### P09：依赖与模型供应链（中高）

- **依据**：Python 直接依赖有版本固定，但 ONNX/科学计算传递依赖、Linux 镜像、模型获取与具体权重许可未形成完整交付证据；此前 Compose 检查不等于镜像构建。资料 L07、S01–S03、S13–S14。
- **最小实验**：干净 Linux 环境构建镜像，记录完整依赖清单、模型 SHA-256/许可来源；限制外网后启动并执行健康＋实际推理；验证 modelLoaded/readiness、服务重启、卷权限与 TTL 清理。
- **建议验收**：目标架构可重建；模型就绪前不接用户计算；断开模型下载站仍可重启；必要许可通知齐全、模型版本可回滚。具体权重商业范围有可追溯依据，不能用第三方模型卡一句话代替。
- **失败替代**：锁传递依赖和镜像摘要、构建期引入经核验权重、采用许可明确且质量达标的模型，或切换有合同授权的商业服务。

## 7. 推荐技术架构

### 7.1 首版架构

```text
微信原生小程序
├─ 页面：今日 / 板面 / 详情 / 月历 / 导出
├─ P1 页面：图片调整 / 记忆查找 / 主题板（按发布决策验收）
├─ 应用层：PhotoTask、编辑会话、草稿与异常恢复
├─ 领域层：Memory / Board / Placement / revision / membershipRevision
├─ 渲染层：统一逻辑坐标＋Canvas 2D＋缩略图/渲染缓存
└─ 存储层：本机原图、主体、缩略图＋版本化元数据/索引
             │ 照片处理副本，不是云备份
             ▼
受控 HTTPS / 云托管入口
├─ 无界面服务身份、请求上限、速率/额度、访问控制
├─ 受限上传/解码 → 图像规格归一化 → ExtractorAdapter
│                                      ├─ 现有 rembg/ISNET CPU
│                                      └─ 商业通用抠图 API（PoC 备选）
├─ alpha/轮廓处理、临时 PNG、受限结果下载、TTL/磁盘清理
└─ 指标/告警：延迟、错误、拒绝、资源、额度；不采集日记内容
```

这是推荐目标图，**并非全部已经实现**。既有页面/领域/渲染/任务层可复用；版本化元数据方案、身份、限流、缓存预算、生产监控和临时结果授权尚待验证和后续实施。

### 7.2 推荐技术栈与理由

| 层 | 推荐 | 选择理由 / 证据与置信程度 |
| --- | --- | --- |
| 小程序 | 继续原生 WXML/WXSS/JavaScript | 已有 8 页与测试，不产生跨端迁移风险；L02/L06，中高 |
| 画布 | Canvas 2D node API，统一 `paint`＋几何工具 | 编辑、预览、导出同一模型，保留当前视觉；L05/W06/W14，中高 |
| 本地记录 | 保留 Memory/Board/Placement v2，按 P02 结果选择文件版本化/分片 | 用户记录不强制上云；先解决单 key，再量化图片容量；L03/W01/W02，中高 |
| 文件 | `USER_DATA_PATH` 下应用专属目录；原图/主体/缩略图区分角色 | 临时路径只用于中间步骤；引用提交后清旧，保留出错恢复；L04/W01，高 |
| 推理服务 | 继续 Python/FastAPI/Pillow/rembg/ONNX CPU 做第一候选 | 已有代码与样例；无须首版训练模型；以质量/压力 PoC 决定是否保留；L07/S01，中 |
| 商业候选 | 腾讯 CI 通用抠图，由服务端适配 | 明确通用能力/价格；输入、地域、质量和开通仍需验证；S04–S06，中 |
| 部署 | 当前 Docker＋Caddy，或云托管容器二选一 | 前者复用配置、便于控制；后者减少部分运维。DNS/TLS/备案不因自动证书消失；L07/S09/S13/S14，中 |
| 管理/观测 | 微信后台＋受限控制台/服务指标 | 不增加无需求的管理产品；先提供可用性与成本可观测性；经验判断，中 |
| 测试 | 现有 Node 测试、Python 接口测试＋独立真机矩阵 | 自动化回归复用；API 替身与真机实测分开记；L06/A03/A04，高 |

正式支持最低基础库/微信版本尚未产品签字。仓库公共配置 2.20.1、私有配置 3.17.3，测试不能由私有版本推导覆盖公共下限。若首发 P1 分享必须可靠关闭小程序入口，需要核验 `needShowEntrance` 3.2.0 起的参数支持；同时隐私接口与平台默认弹窗路径须一并验证。不要仅修改版本字符串就宣称兼容完成。（L02、W07/W09，高；最低版本待确认）

### 7.3 保留的关键接口与一致性原则

现有提取协议 `POST /extract`，multipart `photo` / `taskId`，返回 `cutoutUrl` / `expiresIn` 可作为首版基线。适配层可以统一供应商限制、错误类型和结果域名，避免页面依赖厂商 SDK。

后续建议把失败区分为：不支持格式、文件/像素超限、未授权、额度或限流、推理不可用、结果过期、下载失败、客户端持久化失败。当前 503 包含繁忙和失败，不应将所有异常统一说成照片本身有问题。异步协议只在 P01/P04 证明有需要时增加。（L04/L07；建议中高）

一致性顺序应保持：**写新文件并验证 → 提交关系和版本 → 更新界面成功状态 → 回收旧文件**。处理取消只清自己的未提交文件；全局引用校验后才清共享素材。服务端没有当前已实现的按 taskId 幂等推理，客户端任务幂等不能避免重复推理费用。（L03/L04/L07，高）

## 8. MVP 范围与迭代路线

### 8.1 建议 MVP：保留原 P0 核心目标

包含今日板、拍照/相册、真实自动主体提取与基础边缘/阴影、失败重试/原图降级/取消、原板直接插入、拖动/四角按钮变换、基础背景、文字分类与换图/删除、自动保存恢复、月历每日两个物件、完整导出及相册保存、容量/权限/缺图/网络异常和本地风险说明。

容量治理、隐私、服务保护属于交付这些已有目标所需的技术可靠性工作，不是新增用户业务。**不以取消自动提取、删除原图或提前要求云账号换取“更小 MVP”。**（需求范围 L01；高）

### 8.2 当前工程的发布处理

P1 已在代码中出现，建议将“P0 核心稳定”与“P1 是否随首版发布”作为两个决策。若随首版发布，F13–F17 必须加入真机验收；若延后入口，需要后续明确的发布范围改动，并保留 v2 数据兼容和正确删除语义。本报告不直接隐藏入口、回退模型或恢复旧删除行为。（L01/L08；高）

### 8.3 建议开发/验证顺序

| 阶段 | 顺序与输出 | 进入下一阶段的条件 |
| --- | --- | --- |

### 8.4 第一版不建议新增的能力

复杂刷子精修、多实例主体选择、AI 艺术风格、账号云备份/多设备同步、自动周/月记推送、饮水统计、社区、多人协作、商城，以及没有产品需求的独立管理后台。理由是它们扩大算法/数据/权限/资质或交互范围，并不解除当前 P0 的主要阻碍。（L01；工程建议，中高）
