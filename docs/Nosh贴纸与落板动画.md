# Nosh 白色贴纸轮廓与落板动画

本次对象为 Nosh 1.3.0（132），APK SHA-256：`0828e1165b1fb809a2ac8d6605fdfc01faa82dcdfa07f3ae1586f6525db49af6`。使用现有 REA 环境继续静态分析，复用相同 APK 的证据；没有录制原 APK 的运行画面。

## 已确认的原流程

保存事件通过 `U0.c.g` 启动保存动画。`y2.w.f → n2.S → U0.c.i` 记录结果图的实际位置；`U0.A.b → U0.p → U0.J.a → U0.G → U0.J.c` 绘制贴纸。等待首页板面、图片与目标坐标准备好后完成交接。

| 阶段 | 时长 | 效果 |
|---|---:|---|
| 原位置揭起 | 1000 ms | 顶部开始逐行抬起，轻微横向扩张 |
| 停留 | 500 ms | 保持揭起状态 |
| 准备画板 | 取决于布局和图片就绪 | 等待真实落点 |
| 飞入与压平 | 1000 ms | 矩形四边插值，旋转到目标角度，同时逐行压平 |
| 落地停留 | 120 ms | 平面贴纸覆盖目标，随后交给普通板面渲染 |

普通识别结果路径使用 `cubic-bezier(.4,0,.2,1)`。未发现额外旋转摆动、路径抬高或弹簧弹跳；原先结果图进入页面的 spring 与本动画是两条不同路径。

## 贴纸变形

原应用使用 Android `Canvas.drawBitmapMesh`，10×24 个网格单元。实际图片绘制尺寸为 W×H，幅度 A=0.16×min(W,H)。逐行得到 lift 后，纵向为 `y−.36×lift`，横向轻微扩张；阴影额外偏移 `(0.035×lift, 0.22×lift+3)`。

绘制顺序为黑色轮廓阴影（alpha 62/255）、原图、白色亮面（alpha `int(sin(πp)×34)/255`）。是柔和的揭起/压平，没有背面翻页纹理。

小程序使用连续全屏 Canvas 2D，将每行网格分成两个纹理三角形。原公式在横向为线性，24 行保留相同的变形；三角形裁切略有重叠以消除栅格接缝。每帧沿原公式计算，避免逐帧 setData；阴影和亮面分别对完整蒙版合成一次，避免接缝处叠加变暗或变亮。源图位置和目标位置实测，飞行期间隐藏板面同一件记忆，落地后恢复普通 Canvas 与编辑手柄。动画不新增或修改任何存储记录；后台切换、尺寸变化、关闭、加载失败和超时均可回到已保存板面。

当前开发工具环境中，`lazyCodeLoading: requiredComponents` 产生有类型名、无方法的空动画组件；移除此按需注入配置后，原生揭起、飞行、落地测试通过。本应用体积较小，采用完整加载确保动态组件可用；这不表示所有微信环境都存在相同问题。

## 白色轮廓

`FoodStrokeProcessorImpl` 的 `x1.d.invokeSuspend` 有纯白 bitmapX2 和额外彩色点纹 bitmapX3 两个结果。本次选择纯白贴纸。

- 支撑掩码：alpha > 0。
- 白边半径：`max(6×clamp(bbox长边×.0066,1.5,20),裁切图长边×.04)`。
- 工作长边上限 1500；方形膨胀后两遍 clipped box blur。
- 平滑半径 `clamp(int(stroke×scale×.2),2,6)`，alpha 再做 `clamp((a−128)×12+128,0,255)`。
- 白色底层上叠加原主体，保留背景透明，并再次按透明边界裁切。

在服务端一次生成 PNG，预览、画板、详情与导出使用同一份像素，不在客户端重复描边。旧照片文件不自动改写；新提取的图片使用新轮廓。当前模型接口未暴露原 SDK bbox，使用已裁主体长边代替；Pillow/OpenCV 与 Android 的插值、抗锯齿也可能存在像素差异。
